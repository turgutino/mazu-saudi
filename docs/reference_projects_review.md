# 沙特极端天气参考工程理解与初步评估

## 1. 本轮目标和边界

本轮仅做只读理解，未修改任何参考工程代码，也未用大规模原始数据重跑其完整实验。评估依据是：

- `reference_code/` 中七个已解压工程的 README、配置、标签、训练、评估、Agent 和预报主代码；对大数据、模型和环境文件只核对清单与调用边界，不反序列化未知 pickle，也不读取 `.env`。
- 公开 GitHub 项目 [`turgutino/mazu-saudi-warning`](https://github.com/turgutino/mazu-saudi-warning) `main` 分支在 2026-07-22 获取的临时源码快照。
- 参考工程自带的报告和保存模型仅作为实现完成度证据，不把自报指标默认视为已独立复现。

一个重要前提是：多数工程共用本仓库产生的 2025 年沙特指标 NetCDF，因此它们更像在同一数据底座上提供不同的上层方法，不是八套完全独立的数据系统。

## 3. 工程一：`mazu_saudi_ewai_deploy`

### 3.1 我对它的理解

这是三个本地工程中最像“完整产品原型”的一个：

1. 从本仓库的每日指标 NetCDF 读取格点特征。
2. 为山洪、极端高温、沙尘强风、沿海风浪训练独立 LightGBM。
3. 用 NetworkX 构建概念层和 35,200 格点物理层图谱，对不同灾害使用 D8 下游、风场扇形、沿海向内陆等传播策略。
4. 通过 LLM Function Calling 将预测、KG 查询和案例检索组成自然语言决策答复。

### 3.2 值得复用的部分

- 分层边界比较清晰：数据/特征、模型、空间传播、Agent 工具和 UI 已分开。
- `RiskPropagator` 按灾种区分空间机制的思路值得保留，比“所有灾害共用一种邻域平滑”更合理。
- SHAP 特征贡献、处置矩阵、资源暴露和安全输出校验对竞赛演示有价值。
- 测试数量多，覆盖数据、特征、训练、解释、评估和真实事件脚本，适合当工程参考。

### 3.3 不能直接继承的结论

- 山洪标签是同日 `flash_flood_risk>=1`，特征包含构成该指标的同日降水、CAPE、湿度等。这学到的是规则映射，不是提前预测。
- 沙尘和风浪标签直接由风速/湿度/SST/IVT 等入模变量生成，因此 0.99 级 CSI 是高度可预期的“规则蒸馏”结果。
- 正式 `train_all()` 不做内部留出评估；高分来自其他试验脚本，不是训练 API 自带的可重复保证。
- “真实事件命中”没有核对风险格点与事件地点的重合，而是以全区高风险格点占比判定。它最多是事件日同期性检查，不是独立预报验证。
- 经纬度作为高权重特征时，留一月可能主要在复制固定高风险区，必须增加留区域、留事件和跨年验证。

## 4. 工程二：`孙佳斌-张恒卓-代码-saudi_mazu_agent`

### 4.1 我对它的理解

这是一个强迭代导向的试验工程。它经历了从明显标签泄漏、逐灾种排除直接标签变量，再到 24 日窗口和 7/14 日统计特征的演进。主线 V12 为七灾种分别训练 XGBoost，同时维护城市阈值、规则融合、KG 嵌入试验、ERA5/GSOD 外部数据和 Web/LLM 服务。

### 4.2 真正有价值的发现

- 直接标签泄漏被显式识别并修复，V9 的高分被项目自身标注为“有水分”，这种诚实的版本进化很值得参考。
- 24 日窗口结合短期均值、方差、极值和趋势，确实比单日特征更符合持续性灾害。
- 项目识别到 0.1°日尺度数据对局地对流暴雨存在硬限制，不把所有失败都归因于模型不够复杂。
- RotatE KG 嵌入、手工物理交互项、LightGBM 对照都有负结果，这些“不改善”的试验对论文消融设计有参考价值。
- GSOD 实测标签 + ERA5 2015–2024 线路改变了问题性质：从“预测自己定义的指标阈值”走向“用前 24 日再分析场预测下一日站点实测极端”，这是最有科研价值的本地资产。

### 4.3 需要重做的评估

- V12 将整年的正负格点-日样本打乱后做 85/15 分割。由于相邻样本共享 23/24 天输入，同日邻近格点也强相关，这不是有效的独立测试。
- V12 的城市阈值从同一城市全年输出 P95 直接取值，其他版本甚至用全年标签优化 F-beta；这些阈值不能用在同一年最终测试上。
- “按月分割不适用极端事件”不是正确结论。按月/时间分割性能下降，正是季节分布偏移和泛化困难的证据，不应通过改回随机分割消除。
- GSOD 线路的 AUC 可保留作为 2024 样本外排序能力，但“最优 F1”是在 2024 测试集上搜索阈值得到，需重做为 2015–2021 训练、2022–2023 验证、2024 一次性测试，或滚动年份回测。

## 5. 工程三：`小组3-项昱翔-戚语轩-黄兴民`

### 5.1 我对它的理解

它不是一个以机器学习分类器为中心的工程，而是“数值预报解译 + 概率/规则门控 + 语义知识图谱 + Agent”：

- `schema/operators.json` 记录 91 个指标的表达式和数据源。
- `schema/rules.json` 为山洪、高温、沙尘、沿海湿热定义加权条件、primary gate、probabilistic gate 和严重性。
- RDF/OWL/SPARQL 层提供指标溯源、灾害级联、空间观测和事件查询。
- 实际代码已用 ECMWF IFS 0.25° 预报代替 README 中的 FourCastNet 主路径，将预报场派生为同一套灾害指标再解译。

### 5.2 值得复用的部分

- 指标 DAG、PROV-O 溯源、灾害规则和区域校准都是好的可解释资产，对竞赛答辩和业务演示很有用。
- POT-GPD 用于高温尾部、Gamma/降水经验分位用于干旱区局地阈值，方法方向比统一绝对阈值更合理。
- primary gate + 统计极端度复核的双层结构可以降低“沙特夏季天天高温”导致的基线虚警。
- 直接输入 IFS/AIFS 意味着系统可以从历史检测迈向真正 lead-time 预警，这是正确的业务形态。

### 5.3 当前不能直接信任的部分

- README 与代码不同步：README 说 FourCastNet 且要求 `run_fcn.py`，但交付目录中没有该文件，代码主路径已是 IFS。
- 2025 一年不是气候态。用单年拟合每格点 GPD/Gamma/经验联合分位，参数不稳且会将当年异常当成基线。
- `min(F_1,…,F_k)` 是一个保守的同时极端得分，不等价于已拟合的 Gumbel copula，更不是独立假设下的联合概率。论文中必须重新定义名称和数学含义。
- 最新规则已修复湿热门控方向，但两条 IFS 计算路径仍不一致：有的忽略 SST/低风，有的对风速不取反。
- 百分位查找存在量纲疑点：百分位坐标为 50–99，返回值却裁剪到 0–1，会使大量值饱和，应统一为 0.50–0.99 或保留 50–99 并使用一致阈值。
- IFS 缺某 lead time 时选取目录里第一个文件，可能在不报错的情况下用错预报时效。
- 部分派生仍是业务近似：单时次 `t2m` 代替日最高温，区域场均值代替逐格点气候态计算距平。这些可用于 demo，不宜直接作为论文方法。

## 6. 工程四：`吴诗华-刘贤君-报告+代码+PPT`

### 6.1 我对它的理解

这是一个强调业务闭环的两灾种区域级原型：将每日格点指标按 13 个锚点最近邻聚合为代理行政区特征，分别输出山洪和极端高温连续风险分数，再按“区域×月份”经验分位映射等级。其后串联布尔机理规则、JSON/NetworkX 事件图、符号案例检索、启发式证据置信度、智谱 GLM 报告、FastAPI 和 Streamlit。

PDF 报告、26 页 PPT 和 README 对局限的表述相对克制：明确没有真实灾害标签、只有 2025 单年、百分位不是多年气候态、代理区不是真实行政边界、`evidence_confidence` 也不是校准概率。这些边界意识比直接宣传高准确率更可取。

### 6.2 值得复用的部分

- `NC → 代理区聚合 → 连续分数 → 分位等级 → 证据 → 报告` 的层次边界清楚，API、前端和无 LLM Key 时的模板回退适合竞赛快速交付。
- 洪水侧取区域最大值、P95 和高值信号，高温侧兼顾区域平均、P90 与持续性，体现了灾种差异化聚合。
- 把等级、底层分数、百分位、规则命中、缺失证据和不确定性同时交付，优于只给一个不可解释标签。
- 报告和代码都坚持“LLM 不打分、只解释”，这个角色边界应保留。

### 6.3 当前实现的关键不一致

- 文档声称 `D → D+1`。仓库确有 `targets.py` 用每区 `shift(-1)` 构造次日目标，也有 `train_backup.py` 用前 80% 日期训练、后 20%日期验证；但当前 `scripts/02_train_models.py` 导入的是另一份 `train.py`，该版本用同日输入列构造同日目标、随机打乱行做 80/20 切分，并训练 Random Forest。
- 当前模型文件的修改时间与同日 Random Forest 版本及 `*_model_meta.json` 一致；`OrchestratorAgent` 又读取请求日期本身的行，只是在结果 JSON 中硬编码 `lead_time="T+1"`。因此当前可运行链路是同日风险诊断被标成次日预报。
- 模型目录混有两代结果。同日随机切分元数据给出山洪/高温 R²≈0.994/0.996，这是模型复现自身输入加权规则的结果；较早的次日时序评估则为山洪 R²=0.652、高温 R²=-1.151，后者甚至劣于预测验证集均值。报告/PPT没有披露这一关键负结果。
- 当前 Random Forest 模型在 17:59 被覆盖，但百分位阈值文件仍来自更早的次日模型训练。推理把一代模型的分数与另一代模型的阈值比较，等级量纲不再有保证；而 backup 版阈值本身又用含验证期的全表预测计算，仍有评估泄漏。
- 每个“区域×月份”只有约 28–31 个日样本，单年 P90 非常不稳定，且最终等级按构造必然约有 10%日期为 HIGH；它表达的是年内相对排序，不等于灾害发生概率或业务警戒线。

### 6.4 Agent/KG 链路的科研边界

- 所谓 KG 校验实质是四个布尔阈值的命中比例；`evidence_confidence` 是人工加权启发式分数，不能当成概率或统计置信度。
- 案例相似度只按灾种、区域、月份和规则关键词加分，不比较连续气象场。高温无人工案例时，会从同区同月全年的高值日回溯；示例在 7 月 15 日检索到 7 月 24/28/30 日，发生时间穿越，不能称为历史案例支持。
- 案例 JSON 没有来源链接、事件空间轮廓或可靠性字段，不能直接充当论文 ground truth。
- 工程没有任何测试文件；随源码打包的 Windows `.venv` 约 538MB，而业务 `app/` 仅约 328KB，且文档 Python 3.11 与虚拟环境 3.12 不一致，复现和版本管理需要清理。

这组工程最适合作为**区域聚合、服务编排和解释界面参考**。若要进入自有论文方法，必须只保留一条明确的 `t→t+1` 训练链，重新生成与模型绑定的阈值，加入时间因果约束的案例检索，并在真实事件标签上评估。

## 7. GitHub 工程：`turgutino/mazu-saudi-warning`

### 7.1 我对它的理解

这个工程的核心贡献是把任务从“同日检测”明确改成“次日预测”：

1. 将 365 个指标文件整理为 17 个核心变量+三个标签的统一数据集。
2. 用第 `t` 日特征预测第 `t+1` 日的 `heatwave_day_flag`、`flash_flood_risk>=2` 或沙尘规则状态。
3. 以 1–6 月训练、7–12 月测试，主模型是 `HistGradientBoostingClassifier`。
4. 尝试固定四邻域均值与 GraphSAGE ST-GNN，并按灾种保留效果更好的实现。
5. 增加规则检测、因果文献 KG、预测/实况/相似事件/区域风险/CAP XML/文献检索七个 Agent 工具。
6. 显式报告 PR-AUC、POD/FAR/CSI/HSS、Brier/ECE、可靠性图和集成分歧，并保留负结果。

### 7.2 主要结果应该怎样解读

| 灾种 | 主模型结果 | 正确解读 |
|---|---|---|
| 热浪 | ROC-AUC 0.971，PR-AUC 0.795 | 日尺度持续性强，邻域均值有效，是四个工程中最可信的模型结果之一 |
| 山洪 | ROC-AUC 0.873，PR-AUC 0.089；0.5 阈值 POD 0.10、FAR 0.803、CSI 0.071 | 有排序信号，但稀有事件操作点很差，不能宣称可运营部署 |
| 沙尘 | ROC-AUC 0.887，PR-AUC 0.164，FAR 0.865 | 存在次日信号，但标签仍是规则代理且虚警高 |

ST-GNN 对山洪 ROC-AUC 有所提升，但 PR-AUC 下降，并将风险溢出到静稳日。固定邻域均值改善热浪却恶化山洪。这说明“空间机制必须灾种感知”，是后续论文最值得吸收的实验结论。

### 7.3 仍然存在的科研边界

- 目标仍是规则派生指标，不是沙特 NCM 实际告警、灾情记录或人员/资产损失。
- 只有 2025 一年；半年时序留出比随机分割好，但仍无法证明跨年泛化。
- 数百万“格点-日”不等于数百万独立样本；真正独立的天气过程可能只有几十个。置信区间应按天气过程或日期 block bootstrap，不能按格点独立估计。
- 山洪预测使用的标签包含同一指标体系的复合评分，有系统性自洽风险。
- GitHub API 显示该仓库未声明许可证。可以学习它的方法和评估设计，不应直接复制源码到自有参赛项目。

## 8. 新增工程五：`沙特极端天气风险研判`

### 8.1 最值得借鉴的是科研治理

这组工程把 MAZU 2025 开发统计与 GraphCast 2018/2020 历史回放分开，并把后者准确标为 `retrospective_transfer_replay`。它建立了完整的阶段闸门：

1. 只在 development 数据上搜索方案。
2. 冻结预注册配置、预测文件和 portable SHA。
3. 对独立事件只运行一次系统预测，并将 LLM 第二意见单独锁定。
4. 锁定后才打开 IMERG、SSOD、GHCN 或影响证据。
5. 未过门槛的任务保留 `research_only_blocked`，而不是调阈值直到通过。

它还明确区分 `observed`、`not_observed`、`not_observable` 和 `conflicting`，并把天气、影响和预测制品分开。当影响数据没有可信负例时只报告正例覆盖，不制造准确率。这些做法应进入 Historical Common-Core 的冻结切分、实验注册表和 MAZU Atlas 的审计轨迹。

### 8.2 能吸收的工程资产

- `ForecastArtifact`、`EvaluationArtifact`、`ReportArtifact` 三类版本化制品及 JSON Schema/SHA 验收。
- 24/48/72 小时 lead-time 的明确能力声明，数据分辨率和回放性质不被 UI 隐藏。
- 系统结论与 LLM 意见双轨保存；Agent 只能解释和编排，不能修改科学分数。
- 失败即停止/降级的机器可读状态，以及开发集、独立回放、影响验证的分层报告。
- NetCDF → ADM1 统计 → JSON → KG/报告的服务交接形式，可用于产品层，但论文主评估仍应保留格点和降水对象。

### 8.3 科研边界

- 独立暴雨回放只有少量事件和对照；分类虽好，降水极值仍明显低估，不能据此声称稳定跨区域泛化。
- 高温跨年候选未通过特异度门槛，工程正确地保持阻断状态；这是一项负结果，不是可部署模型。
- 影响层缺少可靠负例，KG 在独立暴雨集没有触发，不能用“图谱覆盖”替代预测技能。
- 目录未发现许可证。可以 clean-room 重建锁、Schema 和审计思想，不复制源码。

## 9. 新增工程六：`生产实习最终报告-郭展宏-2023040087-翁联桥-2023040088`

### 9.1 值得重建的部分

- 将事件概率扩展为 T+1/T+2/T+3，并按时效报告技能衰减。
- Analog Ensemble、多 K 近邻、树模型/TCN 混合、逐城市诊断和空间留出，可组成有竞争力的 baseline suite。

- DuckDB、模型元数据、Streamlit/Neo4j 页面展示了数据—模型—解释—服务的完整工程形态。

### 9.2 为什么不能沿用现有成绩

- 同一日期被扩成大量城市 3×3 邻域与均匀网格样本，随后在月份内随机抽样训练/测试；同日高度相关格点和重复未来标签跨集合，导致严重空间—时间泄漏。
- 多个最终优化脚本在随机 `train_test_split` 的 `y_test` 上拟合 quantile calibration、选择 BestDIFF/BestCSI 阈值，并在同一集合汇报，属于测试集污染。
- 数据末端没有未来观测时直接把标签填为 0，将 `not_observable` 错当普通负例。
- 代码中的 persistence baseline 实际复用了 climatology 概率，不是真持续性基线。
- `flash_flood_risk` 等派生规则既进入特征又参与标签定义，部分任务仍是规则复现而非独立事件预测。

因此只能复用实验“形状”，不能复制分数。重做协议必须是日期/天气过程级冻结切分，训练集建立 analog 库，验证集独立校准和选阈值，最终测试集只评一次。

## 12. 给自有方法的更新结论

如果目标同时是竞赛和发论文，最合理的起点不是再造一个“更大 Agent”，而是先把下列科学问题做实：

1. **实测或官方事件标签**：优先建立 GSOD/NCM 告警/灾情报道的时空事件表，把“规则派生标签”降级为辅助任务或 weak supervision。
2. **严格的时空验证**：以年份/天气过程/区域做完整 block split，阈值只用验证集调整，测试集只评一次。
3. **灾种感知的多尺度空间机制**：对热浪使用平滑/大尺度背景，对山洪保留局地极值并引入地形、上游和降水峰值特征，对沙尘引入风向与沙源路径。
4. **可靠性而不只是 AUC**：必须同时报告 PR-AUC、POD、FAR、CSI、HSS、Brier/ECE、置信区间和预警 lead time。
5. **真实预报场接入**：历史指标模型评估和 IFS/AIFS 在线预报解译分开设计，对不同 lead time 独立验证。
6. **Agent 只做最上层编排**：Agent 负责查询、解释、告警格式和行动建议，不参与或改写底层科学分数。
7. **实验制品先于漂亮页面**：每次正式运行冻结数据版本、切分、阈值、校准器、模型、预测和 SHA；页面只读取制品，不在请求时偷偷重算规则。
8. **类比/模板只能是训练期资产**：Analog 库和机制原型必须按折构建，不能从验证、测试或未来事件提取。

简单地说，新增代码使实施优先级发生了一次重要调整：

1. 第一优先级吸收 `沙特极端天气风险研判` 的 **预注册锁、真值隔离、失败降级和制品 Schema**。
2. 第二优先级 clean-room 重建 **Analog Ensemble、多时效可靠性诊断和训练期机制原型**，作为 MCR-Precip 的强基线与消融。
3. 第三优先级继续保留既有工程的 **GSOD/IMERG 独立评估、灾种/机制差异化传播、IFS 解译和受控 Agent 服务**。
4. 明确拒绝 **随机格点切分、全年来构造模板、测试集校准/调阈值、不可观测样本填负例和概率直接映射官方预警**。

这些资产应在自有时间因果合同下重新实现，而不是直接拼接原代码或继承其自报成绩。
